## 1. 가장 먼저 지킬 계약

1. **도면이 구조·비례·칸수·문/창호 배치·측후면을 결정한다.**
2. **지정 V3 원본이 색감·재질·기와·목재·석재·선화·건물 정체성을 결정한다.**
3. 현장 사진은 도면에서 모호한 입면, 사용 흔적, 글자와 재료를 확인하는 보조 증거다.
4. 사랑채 3D 자료는 보이지 않는 후면과 ㄱ자 연결 관계를 이해하는 보조 자료일 뿐이다. 3D 재질·렌더·기와 모양을 2D 화풍의 정본으로 사용하지 않는다.
5. 원본 보존 PNG만 원본과 바이트 및 픽셀이 동일하다. 생성된 8방향 PNG는 원본과 도면을 참고한 **2D 파생 이미지**이며 “원본과 픽셀 동일”이라고 표현하지 않는다.
6. 3D 재생성은 중단된 방향이다. 2D 이미지 편집으로 시점과 방향을 확장한다.
7. 검토 자료와 작업 파일은 `assets_unused/pending_review`에 둔다. 런타임 승격은 별도의 사용자 승인과 해시 검증을 거친다.

## 4. 폴더 안의 파일 역할

각 건물 폴더의 파일 역할:

1. `references/canonical_source/` — 사람이 지정한 V3 시각 정본
2. `references/blueprints/` — 구조 정본
3. `references/photos/` — 현장 보조 증거(솟을대문)
4. `references/structural_model/` — 구조 보조만 허용(사랑채)
5. `*_source_original_exact.png` — 정본의 바이트 동일 보존본
6. `*_raw.png` — 배경 제거 전 작업 결과
7. `*_transparent.png` — 알파 처리된 4×2 검토 시트
8. `transparent_views/` — 해당 버전에서 시트를 분리한 원래 작업 프레임. 역사 보존용이며 현재 런타임과 같다고 가정하지 않는다.
9. `revisions/` — 후속 수정 버전의 전체 작업 파일(있는 건물만)
10. `runtime_views/` — 현재 정본 런타임 8장의 패키지 스냅샷. 정확한 revision과 해시는 건물별 `README.md`, `MANIFEST.json`, `CANONICAL_PROMOTION.json`에서 확인한다.
11. 후처리 스크립트 — 배경 제거와 시트 분할을 재현하는 작업 도구

출처끼리 충돌하면 위 순서가 아니라 다음 의미별 규칙을 적용한다.

- 구조 충돌: 도면 우선
- 화풍·재질·색 충돌: V3 정본 우선
- 도면에 없는 현장 표식·마모: 현장 사진 참고
- 3D와 도면 충돌: 도면 우선

## 5. 다음 건물 제작 절차

1. 사용자가 지정한 V3 정본 파일을 확정하고 SHA-256을 기록한다.
2. 정본을 `*_source_original_exact.png`로 바이트 복사하고 즉시 해시 일치를 검증한다.
3. 해당 건물의 평면·정면·배면·좌우측면·지붕평면·단면·상세 도면을 한 폴더에 모은다.
4. 도면이 없는 면은 일반 한옥 관습으로 임의 창작하지 말고 “근거 부족”으로 표시한다. 현장 사진이 있으면 보조한다.
5. 먼저 정면 한 장에서 약 28° 카메라와 원본 화풍을 승인받는다.
6. 그 시점을 고정해 45° 간격 8방향을 만든다. 각 방향에서 건물의 칸수와 부재는 같은 건물이어야 한다.
7. 밝은 체크 배경은 연결 영역 기반 알파 처리로 제거한다. 건물 내부의 밝은 회벽·한지는 색상만으로 지우지 않는다.
8. 4×2 시트를 384×512 8장으로 분리하고 인접 셀 잔여물을 제거한다.
9. 바닥선, 실루엣 여백, 축척, 기둥과 계단의 알파 손상을 육안 비교한다.
10. 이 `README.md`가 있는 `turnaround_2d` 폴더로 이동해 `python -X utf8 validate_packages.py --package <package_name> --write-manifests`를 실행한다.
11. 생성된 `MANIFEST.json`과 `SHA256SUMS.txt`를 검토한다.
12. 사용자 시각 승인 후에만 런타임 폴더와 카탈로그를 갱신한다.

## 6. 런타임 연결 지점

현재 앱의 2.5D 회전·배치 시스템은 다음 파일을 중심으로 동작한다.

- `lib/data/ildu_turntable_catalog.dart` — 8방향 파일, 알파 경계, 공통 뷰포트 등록
- `lib/widgets/sori/hanok_turntable_2d.dart` — 45° 회전과 확대/축소 미리보기
- `lib/screens/ildu_world_screen.dart` — 지도 팬, 건물 드래그, 방향, 건물별 크기 조절과 저장
- `assets/illustrations/personal_hanok_v3/turnarounds/` — 런타임 PNG

런타임 교체 시 검증할 항목:

- 승격 대상 revision, 패키지 `runtime_views/`, 앱 런타임 8장의 SHA-256 일치. 과거 `transparent_views/`와 이전 revision은 이력 보존용이며 현재 정본으로 간주하지 않는다.
- 카탈로그의 alpha bbox와 실제 PNG 불투명 경계 일치
- 지도 확대/축소 1.0~2.2배, 지도 이동, 건물 드래그, 45° 회전, 건물별 크기 저장이 서로 충돌하지 않음
- 기존 건설 단계와 다른 건물의 위치·방향·크기 저장을 손상하지 않음

## 7. 사랑채 단계별 건설 설계 인수인계

사랑채 파일 안의 `handoff/construction_pilot/`은 다음 건물 제작 때 참고할 승인 문서와 구현 스냅샷이다.

핵심은 “모든 건물을 무조건 8단계”가 아니다. 초기 8단계 계약에서 발전해, **실제 공법과 건물 의미에 맞춰 건물별 단계 수를 가변**으로 한다. 공통 단위는 단계 번호가 아니라 `processTag`다.

대표 태그:

`site → foundation → frame_posts → frame_beams → rafters_sanja → roof_bed → roof_tiles → floor_numaru → wall_infill → doors_changho → identity_finish → complete`

사랑채는 12단계가 적절하지만 작은 문은 4~7단계일 수 있다. 완성 단계는 새로 그린 이미지가 아니라 지정 V3 정본을 그대로 사용한다. 중간 단계는 하나의 공통 좌표계와 누적 레이어를 공유하고, 앞 단계의 완성 부재가 다음 단계에서 이동하거나 사라지면 실패다.

다음 세션은 반드시 아래 두 문서를 순서대로 읽는다.

1. `ildu_sarangchae_v01/handoff/construction_pilot/specs/2026-08-28-ildu-v3-blueprint-led-eight-stage-assets-design.md`
2. `ildu_sarangchae_v01/handoff/construction_pilot/specs/2026-08-29-ildu-variable-construction-cultural-lernpath-design.md`

그 뒤 앱 연결이 필요할 때만 같은 `specs/`의 `2026-08-29-ildu-sarangchae-variable-construction-app.md`와 `ildu_sarangchae_v01/handoff/construction_pilot/implementation_snapshot/`을 읽는다. 이 자료는 스냅샷이며 현재 `main`의 런타임 권위가 아니다. 먼저 최신 Git 상태와 현재 코드를 대조해야 한다.

## 8. 완료와 미완료를 구분하는 법

자동 검증 통과가 의미하는 것:

- 파일이 있고 8장이다.
- 384×512 RGBA이며 실제 투명/불투명 픽셀이 모두 있다.
- 정본 보존본과 canonical source의 SHA-256이 같다.
- 런타임 파일이 존재할 경우 바이트가 같은지 확인됐다.

자동 검증이 증명하지 못하는 것:

- 도면 고증이 완벽하다.
- 좌우·후면 창호와 기둥 수가 정확하다.
- 원본 화풍이 사람 눈에 충분히 유지됐다.
- 배치 화면에서 크기와 바닥 접점이 자연스럽다.
- 생성된 8방향이 원본과 픽셀 동일하다.

위 항목 전부는 사람의 시각·도면·인게임 승인이 필요하다.
