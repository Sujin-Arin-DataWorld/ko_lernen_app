# 일두고택 완성 계획

## 목표와 기준

기존 일두고택 12채를 `gye`의 부드러운 일러스트 화풍으로 다듬는다. 목재의 세월과 결, 돌의 불규칙한 표면, 기와의 곡선을 함께 살린다. 전체 색과 붓결은 조화시키되 건물마다 목재의 수종·마모·명암·무늬 위치가 달라야 한다. 작은 모서리 수치 조정만으로 미술 완성을 선언하지 않는다.

- 기존 건물 축·문짝·경첩·현판·승인 원화를 유지한다.
- 승인된 창고와 3번째·4번째 문 사이 담장 접점은 유지한다.
- 지붕은 기본 화면에서 보인다. 목재 확대 화면에서만 임시로 숨긴다.
- 기와는 따뜻한 먹회색과 무광 표면을 공유하며 건물별 마모는 달리한다.
- 돌 수정 범위는 **건물 기단 윗면·계단·주변 돌 포장**이다. 마당은 흙으로 유지한다.
- 정원·정자는 본 건물 미술이 정리된 뒤 진행한다. 제거한 조잡한 초안은 되살리지 않는다.
- 현 단계는 로컬 검토 후보다. 앱 적용·성능 검증·최종 미술 승인은 별도 단계다.

## 진행 순서와 완료 조건

### 1. 사랑채·중문채 넓은 판벽부터 마무리

현재 새 목재 적용은 `Sarang golden aged timber`, `Sarang vertical timber grain`, `Jung dark walnut` 3개 재질이다. **아래 재질은 아직 기존 표현이라 먼저 확인하고 수정한다.**

- 사랑채 `Sarang floor grain 0`, `Sarang floor grain 1`, `Sarang floor grain 2`: `V25.left horizontal boarding` 등 넓은 판벽.
- 중문채 `Jung plank 0`부터 `Jung plank 3`: 뒤쪽 부속 판벽과 가로대.
- 적용 스크립트: `apply_heritage_wood.py`. 새 재질이 추가되면 `audit_requested_craft.py`의 3재질 전제도 실제 범위에 맞춘다.
- 원화 해상도와 매핑을 지키도록 `bake_estate_legacy_palette.py`의 `gyeHeritageWoodV1` 경로를 유지한다.

완료 조건: 같은 카메라의 정면·확대에서 넓은 판벽까지 목재로 읽히며, 부재마다 결 시작점·폭·명암이 다르고 반복 무늬가 눈에 띄지 않는다. 자로 잰 듯한 판재의 균일함을 부드럽게 다듬되 축·문 조작은 보존한다.

### 2. 돌 상면과 계단의 남은 매끈함 정리

`apply_platform_stone.py`의 새 돌 상면을 기준으로 큰 디딤돌·계단·착지석에 남은 평평함이나 줄무늬를 확인한다. 전체 흙마당을 돌로 채우지 않는다. 돌의 색·크기·이음·마모가 주변 기단과 자연스럽게 이어져야 한다.

### 3. 나머지 건물을 한 채씩 같은 화풍으로

안채의 사진 명암·흐린 결을 우선 확인한다. 이후 안사랑채·아래채·안곳간채·곳간채·대문채·사당·화장실 두 채를 순서대로 검토한다. 창고는 승인 원화를 기준으로 주변과 조화만 확인한다. 기와는 색만 맞춘 상태에 멈추지 않고 질감·타일 반복·처마 명암도 함께 검토한다.

매 회차 한 가지 눈에 보이는 미술 문제를 해결한다. 대표 정면·확대 2~3장과 전체 화면으로 전후를 비교한다. 한 건물의 검토를 마친 뒤 다음 건물로 넘어가고, 매번 전체 원본을 다시 만들지 않는다.

### 4. 고택 전체 연결과 동선 확인

곳간채 뒤 여백, 담장 접점·꽃담 문양·지붕 이음, 기단과 담의 겹침, 문 회전 공간을 확인한다. 창고 승인 접점은 유지한다. 전체/위쪽 배치/주요 마당 화면에서 누락·중복·떠 있는 부재가 없어야 한다. 숫자 검사와 함께 실제 화면을 확인한다.

### 5. 정원·정자, 이후 앱 적용

본 건물의 미술을 사용자와 확인한 뒤 사당 뒤 정원·정자를 설계한다. 고택과 어울리는 나무 표현을 먼저 작은 범위에서 검토한다. 앱 적용 단계에서 터치·문 조작·카메라·모바일 성능·파일 용량·다운로드 경계를 검증한다. 현재 333MB 검토 GLB는 완성 앱용 전달물로 간주하지 않는다.

## 원본 보관과 코드 진입점

- `northern-court/checkpoint/`: 현재 원본+검사 기준 원본+외부 이미지의 바이트 보존 압축본, 각 파일 경로·해시 목록. 압축본 내부 멤버를 원본 SHA와 대조했다.
- `northern-court/materials/`: 새 그림과 생성 프롬프트·출처.
- `northern-court/review-checkpoint/`: 현황 HTML·확인 화면·현재 viewer·구성 manifest. GLB 청크는 재생성 대상으로 로컬에 보존한다.
- 역사적 `.blend/.blend1`, GLB, 실패한 범위 조정 초안, 로그는 기존 폴더에 보존하며 원격 체크포인트의 정본이 아니다. 실패 초안 `estate-fabric-craft-attempt-scope-review.blend`를 재개 원본으로 쓰지 않는다.
- `tool/hanok_scene/apply_requested_craft.py`: 이번 요청 적용 순서. 이미 적용된 원본에 무턱대고 재실행하지 않는다.
- `export_current_estate.py`: 현재 장면의 검토용 내보내기; `audit_estate_fabric.py`: 원본/웹 검사.
- `complete_estate_fabric.py`: 이전 기준 장면에서 전체 후보 생성. 다른 옛 워크트리의 geometry 모듈을 참조하는 역사적 경로가 있어 현재 작업 재개 시 실행하지 않는다.

같은 컴퓨터에서는 살아 있는 `estate-fabric.blend`를 계속 사용한다. 다른 위치에서 압축본을 복구할 때는 `native-dependencies.json`의 `archiveFile`로 외부 이미지를 재연결한 **별도** 장면을 저장한다. 바이트 보존 원본은 덮어쓰지 않는다. 로컬 서버가 꺼져 있으면 기존 리뷰 dist에서 같은 포트를 사용한다.

원격 체크포인트는 Git 파일 크기 제한 안에 들어가는 3개 조각이다. `python tool/hanok_scene/restore_estate_checkpoint.py 새출력경로.zip`으로 조립·검사한다. 압축본의 `native/estate-fabric.blend`, `native/detail-redraw.blend`와 `images/`를 별도 복구 폴더에서 확인한다. 원격 HTML의 정지 화면은 포함되어 있고 3D 청크는 기존 로컬 서버에 남아 있다. 새 컴퓨터에서는 내보내기로 다시 생성해야 한다.

종료 시 `graphify update .`를 한 번 실행한다. 커밋/푸시/앱 승격은 당시 사용자 권한을 확인한다.
