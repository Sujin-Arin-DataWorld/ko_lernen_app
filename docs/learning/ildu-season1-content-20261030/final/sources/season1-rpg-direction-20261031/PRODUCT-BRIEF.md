# 한글소리 · 이름을 가진 주인공과 이어지는 대화

2026-10-31. ECC product-lens의 제품 진단과 UI UX Designer의 화면/흐름 비평을 적용한 **방향 판단 문서**다. 구현 명세·승인된 새 화면·앱 동작 검증은 아니다. 새 이미지/코드/설치/배포/커밋은 실행하지 않았다.

## 사용자가 이번에 명시한 의도

2006년 무렵 테일즈위버에서 가장 되살리고 싶은 경험은 선택한 캐릭터 중심의 개별 퀘스트들이 하나의 본편으로 이어지고, 짧은 애니메이션과 채팅형 대화로 이야기를 겪는 감각이다. 한글소리에서는 유저가 이야기 속 이름을 정해 주인공이 된다. 외형 생성은 완성 시간을 늘리므로 우선 이름만 받는 방향이다. 이 내용은 이번 사용자 답변이며 자유 이동·전투·MMO가 최우선이라는 뜻으로 해석하지 않는다.

기존 제약: EN/DE UI, 실제 Lora500/Source Sans3, C안 재료, 정본 캐릭터와 R16 기하 보존, 학습 원본/도움/독립 수행/복습/본편/공정/재화 구분, 앱 코드 변경 보류.

## 원래 이야기와의 일치

`reference/STORY_V3_5.md` §2.1(51~69행)은 이미 Player/{이름} 주인공, 수진 동행, NPC별 호칭, 이름 표시와 고정 TTS 분리, 입문자/경험자의 같은 본편 합류를 명시한다. 이번에는 그 체계를 화면에 드러내는 것이 핵심이다. 외형 커스터마이징은 원안의 장기 방향으로 남기고 사용자 최신 지시에 따라 첫 제작 범위에서는 미룬다.

현재 gate-de.png는 정본 이미지를 확인하는 카드에는 유용하지만, 유저의 존재/이전 행동/대화의 연결을 보여 주지 못한다. 내 직전 제작은 원본 합성·조판에 집중하면서 주인공과 사건의 인과를 충분히 살리지 못했다.

## 제안하는 첫 경험

1. EN: `What should we call you in this story?` / DE: `Wie sollen wir dich in der Geschichte nennen?` 이름/별명을 입력한다. 실명은 요구하지 않고, 건너뛰면 여행자 호칭으로 진행하며 나중에 바꿀 수 있게 하는 것이 제안이다. 아바타 생성은 두지 않는다.
2. 프롤로그는 플레이어 시점과 현재 정본 동료를 사용한다. 플레이어의 대사에는 선택한 이야기 이름을 화자로 표시한다. 수진이 단순 설명자가 아니라 그 이름의 동행자에게 말을 건넨다.
3. 첫 공부책: 내가 책을 살피고 첫 글자를 복원하는 선택/학습 행동 → 탈선비 귀환 → 도깨비의 반응. 이 원래 인과를 짧은 연기와 대화로 보여 준다. 지원 참여도 같은 본편에 들어가며 독립 발화 성공을 꾸미지 않는다.
4. 이후 NPC 만남은 같은 플레이어와 이미 공개한 사건을 이어받는다. 모든 NPC가 매번 새 사람처럼 자기소개하지 않는다. 캐릭터별 단편은 공통 본편의 공개 순서를 따라 합류한다.
5. 중문 문지기는 아는 동료의 역할 놀이다. `LQ05_GATEKEEPER.md`의 소개 → 한 대목을 놓침 → 다시 부탁 → 같은 전체 내용 반복 → 길을 비켜 줌의 인과를 사용한다. 도깨비가 플레이어를 잊은 것으로 만들지 않는다.

이 목록은 새 게임 엔진의 구현 단계가 아니다. 기존 자료를 활용할 방향 예시다. 첫 공부책 직후 A1.1로 건너뛰지 않으며 중간 교육과정을 유지한다.

## 이름만 넣는 가짜 개인화를 피하기

- **호칭:** 수진·조이·탈선비·도깨비는 원래 말투와 친밀해지는 시점을 유지한다. 도깨비는 초반부터 이름을 남발하지 않고 정본대로 변화한다.
- **발화 주체:** 플레이어의 선택/말은 내 이야기 이름의 말풍선으로 나타난다. 정해진 대사를 눌렀다는 사실과 자유 발화/독립 수행은 구분한다.
- **국소 반응:** 같은 결말로 합류해도, 도움을 청했는지 직접 시도했는지에 따라 바로 다음 반응은 실제 기록에 맞게 달라진다. 모든 선택이 같은 한 줄이면 장식적 선택에 그친다.
- **기억:** 재방문 시 이미 한 소개/부탁을 기억하는 반응을 사용한다. 실제 기록이 없는 일을 '지난번 네가 했다'고 말하지 않는다.
- **역할 분리:** 유저의 이야기 이름과 학습용 가상 소개 카드의 이름은 별개다. 카드가 하린이라면 그것을 역할 연습으로 분명히 하고 실제 플레이어 이름을 바꿔 저장하지 않는다.
- **음성:** v3.5에 이미 있는 이름 텍스트/고정 호칭 음성 분리 규칙을 사용한다. 임의 외국 이름의 실시간 TTS 발음이나 모든 대사 재생성을 첫 범위의 필수 조건으로 삼지 않는다.

## 현재 화면의 UX 비평

| 문제 | 판단 | 바꿀 방향 |
|---|---|---|
| 회색 바탕 위 큰 도깨비와 축소 건물이 전시물처럼 분리 | 몰입 목표에 주요 문제 | 장소의 맥락을 먼저 보여 주고 대화 인물 초상을 대화 창과 연결 |
| 내 이름/내 응답/이전 사건이 없음 | 주인공 감각에 주요 문제 | 플레이어 화자와 실제 행동을 끼워 넣고 후속 반응으로 이어지게 함 |
| 한 화면에 대사·별도 설명·큰 시작 버튼이 모두 쌓임 | 대화의 속도와 위계 문제 | 한 번에 한 대화 차례와 현재 필요한 반응을 표시. 번역/도움은 명시적 조작으로 펼치기 |
| 화면을 보고 다음에 NPC가 무엇을 할지 알 수 없음 | 행위 결과의 가시성 문제 | 재요청하면 실제로 같은 말을 반복하고, 사건이 끝나면 다음 장면/대사가 바뀌게 함 |
| 정지 이미지로는 연기·저장·오디오/다시 보기의 연결을 검증할 수 없음 | 미평가 | 다음 검증은 반복 가능한 짧은 장면 흐름; 현재 이미지를 앱 동작 완료로 판정하지 않음 |

수치 점수/실사용자 성과는 만들지 않는다. 위 심각도는 첨부 화면과 몰입 목표를 비교한 디자인 판단이다.

## 화면·연출 제안

상단은 짧은 챕터/장소 표시, 중앙은 현재 장소, 하단은 한 개의 대화 창으로 정리한다. 선택된 NPC 정본 초상과 플레이어의 이름/응답이 번갈아 나타난다. 긴 독일어에서도 본문17px 기준을 유지하고 텍스트를 억지로 축소하지 않는다. 읽기/도움/나가기의 명시적 버튼과 선택 대안을 둔다. 타자 효과는 즉시 전체 표시가 가능해야 하며 영상은 건너뛰어도 사건의 뜻이 남아야 한다.

짧은 애니메이션은 책장·시선/기존 검수 포즈·사건 전환·첫 각성처럼 원인이 달라지는 순간에 쓴다. 이미지가 있다는 이유로 다방향 걷기, 팔을 벌리거나 빗장을 고치는 동작 원본이 준비됐다고 주장하지 않는다. 우선 현재 원본과 저작 대화로 장면을 검증하고, 부족한 반응 포즈/환경을 정확히 골라 별도 제작한다.

R16 중문 현재 원본은 배경 포함 카탈로그 래스터다. 사랑채의 새 투명16공정+독립 완성본 묶음이 중문/전체 필드까지 투명하다는 뜻은 아니다. 실제 장면 합성에는 맞는 배경/카메라/분리본 검토가 더 필요하다. 기둥·지붕·창호를 AI로 새로 그려 필드를 메우지 않는다.

## 대화가 이어지는 느낌과 시스템의 경계

처음에는 저작한 대사와 제한된 조건 분기로 만든다. 자유 AI 채팅을 본편의 진실·새 단서·결말 소유자로 두지 않는다. 본편과 공개 사실은 같은 줄기로 합류하고, 플레이어의 도움/응답에 대한 짧은 반응만 달라질 수 있다. 재생/미디어 실패는 학습자 오답으로 취급하지 않는다. 저장 실패에는 완료를 가장하지 않고 같은 응답을 유지한다. 도움·다시 보기·복습 누락으로 이미 본 이야기를 취소하지 않는다.

중문 대화 완료로 완공 폭풍·기억30%·12공정 완료·새 엽전을 동시에 지급하지 않는다. 연이의 과거와 두 번의 마지막 대답을 플레이어 이름에 맞춰 다시 쓰지 않는다. 플레이어는 지금 기록을 읽고 전하며 관계를 바꾸는 주인공이다.

## 검증 제안

동일한 학습 목표와 비슷한 문구/도움 조건을 가진 현재 카드형과 짧은 대화형 장면을 비교한다. 먼저 작은 사용성 관찰로 혼란을 찾고, 인과적 학습 효과는 별도 통제된 검증으로 판단한다. 표본/일정/비용/리텐션 상승률을 현재 자료로 추정하지 않는다.

- 자신이 이야기 속 누구인지, 어떤 행동으로 NPC의 다음 반응이 달라졌는지 설명할 수 있는가.
- 다음 조작과 도움을 찾을 수 있는가. 대화 연출 때문에 실제 학습 시작이 불필요하게 늦어지지 않는가.
- 이야기를 이어 보고 싶은가와 목표 표현을 해낼 수 있는가를 따로 확인한다.
- 도움 사용/독립 수행/다음 날 회상을 분리한다. 다음 날 회상 실패가 본편/건축 소유를 되돌리지 않게 한다.
- 같은 장면 재생에서 중복 완료/엽전이 생기지 않는지, 중단 후 올바른 대화 차례로 돌아오는지는 실제 구현 단계에서 검증한다.
