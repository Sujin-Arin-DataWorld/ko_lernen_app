# Web Firebase external release setup

The checked-in project deliberately contains no Web Firebase option, Auth
domain, OAuth redirect value, App Check site key, Apple team value, or iOS
plist. Complete this runbook only in the Firebase and Apple accounts owned by
the release operator. Do not invent values to make a local build pass.

## 1. Register the actual Firebase apps

In the existing `ko-lernen-app` Firebase project, register the production Web
app. Select the real hosting domain(s) and application identity; do not copy a
Firebase app ID from another project.

From an authorized release workstation, generate configuration for the actual
Android, iOS, and Web registrations together. FlutterFire must make the
selection rather than a hand edit of an app ID:

```bash
set -euo pipefail

: "${FIREBASE_PROJECT_ID:?Set FIREBASE_PROJECT_ID to the existing Firebase project ID}"
command -v flutterfire >/dev/null
test -f pubspec.yaml

flutterfire configure --project "$FIREBASE_PROJECT_ID" --platforms android,ios,web
```

Review the generated `lib/firebase_options.dart` and `firebase.json` against
the selected Firebase Console applications before using them. Keep the local
`ios/Runner/GoogleService-Info.plist` ignored and out of commits. The iOS
target-membership, URL-scheme, signing, and archive gate remain in
[the iOS external setup runbook](ios-external-setup.md).

## 2. Configure Authentication and redirects

In Firebase Console > Authentication:

1. Add every real Web origin used by the release as an authorized domain.
2. Enable and verify the Google provider with its real authorized JavaScript
   origins and redirect URIs.
3. Enable the Apple provider and configure its real Service ID, return URL,
   key, and private-email relay requirements. The Firebase Auth handler URL
   must use the actual Firebase project domain selected by the operator.

Do not place OAuth client IDs, Apple key IDs, private keys, or redirect values
in this repository unless they are already a deliberate, reviewed public app
configuration generated by FlutterFire.

## 3. Configure Web App Check and inject its key at build time

Create a Firebase App Check Web reCAPTCHA v3 provider for the registered Web
app. Give the resulting public site key to the release build through the
environment only:

```bash
set -euo pipefail

: "${FIREBASE_WEB_APP_CHECK_SITE_KEY:?Set the Firebase App Check Web reCAPTCHA v3 site key}"
flutter build web --release \
  --dart-define="FIREBASE_WEB_APP_CHECK_SITE_KEY=$FIREBASE_WEB_APP_CHECK_SITE_KEY"
```

The app intentionally fails closed after Firebase initialization when Web is
configured but this value is empty: App Check activation throws before auth,
backup/restore, or other protected cloud startup calls can begin. Never add a
fallback key, a sample key, or a checked-in environment file to bypass that
gate.

## 4. Operator verification after configuration

Run these checks with real authorized accounts and devices:

1. Web: sign in, refresh, sign out, and verify the correct authorized-domain
   behavior.
2. Web: create offline course progress, reconnect, and verify Firestore
   backup/restore and conflict handling without clobbering data.
3. Web: invoke an App-Check-protected callable and confirm the server accepts
   it only with valid App Check.
4. iOS on macOS/Xcode: run the iOS Firebase configuration gate, test Google
   and Apple sign-in, push/APNs delivery, and a physical-device archive.

Source-only checks such as `flutter test` and `flutter build web --release`
cannot prove Firebase Console registration, authorized-domain setup, App
Check enforcement, Apple signing, APNs, or live multi-device synchronization.
